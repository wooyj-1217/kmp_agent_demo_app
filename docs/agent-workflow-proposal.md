# 역할 분담과 변경 맥락 관리 제안

상태: 과거 운영 설계 제안. 역할·맥락 관리의 현재 절차는 [프로젝트 에이전트 운영](agent-workflow.md)이 대체한다. 아래는 제안 당시 근거로 보존한다. 사용자는 메인 중심·필요시 위임 방향에 동의했다. 아래 세부 절차는 자동 실행기·승인 게이트·전체 이력 수집 기능으로 구현된 것이 아니다. 앱 기능이나 저장 방식을 이 문서로 변경하지 않는다.

## 역할 분담

| 담당 | 기본 책임 | 사용하는 때 |
| --- | --- | --- |
| 메인 | 사용자 의도·범위 확인, 변경 영향 분석, 작은 구현, 통합, 최종 보고와 맥락 갱신 | 모든 작업의 책임자. 핵심 제품 결정을 직접 사용자와 확인 |
| 조사/구현 서브에이전트 | 범위가 분리된 질문·파일 묶음의 결과 반환 | 병렬로 끝낼 수 있고 인계 비용보다 이득이 있을 때만 호출 |
| 별도 리뷰어 | 원래 요청·확인 근거·기존 정책과 변경 결과 대조 | 중요한 기획 결정, 데이터/API·공유 로직·마이그레이션 등 위험이 있는 변경 |
| 스크립트/도구 | 정해진 빌드·테스트·사용량 집계·무결성 확인 | 반복 가능한 기계적 검사. 검사가 사용자 제품 결정을 대신하지 않음 |

역할마다 상시 서브에이전트를 배정하지 않는다. 단순 문구·스타일 변경에 전체 기획→디자인→개발→QA 인계 사슬을 반복하지 않는다. 서로 의존하는 작은 단계는 메인이 이어서 처리한다. 기존 하네스의 필수 검토를 바꾸려면 별도의 절차 변경으로 다루며 이 제안만으로 우회하지 않는다.

서버·클라이언트처럼 큰 구현을 나눌 때는 데이터/API 계약을 먼저 맞추고 소유 파일과 통합 책임을 고정한다. 같은 파일·출력 폴더·시뮬레이터를 동시에 다루지 않게 조율한다. 작업 트리를 나눠도 최종 통합·회귀 확인 책임은 메인에 있다.

## 맥락의 위치와 구분

[여백 맥락 진입점](fresh-memo/context.md)을 짧게 유지하고 상세 근거는 링크한다. 맥락은 각 성격에 맞는 자료로 관리한다.

| 자료 | 담을 내용 | 잘못된 사용 방지 |
| --- | --- | --- |
| 사용자 결정·미결정 기록 | 무엇을 누가 결정했는지, 근거, 영향, 대체한 결정 | 에이전트 제안·QA PASS를 사용자 승인으로 바꾸지 않음 |
| 현재 요구·디자인·데이터/API 계약 | 유지해야 할 제품 동작과 인터페이스 | 대화에만 남기거나 구현 편의로 조용히 축소하지 않음 |
| 현재 코드·검증 결과 | 실제 구현과 실행된 범위·버전·제한 | 구현 사실이 곧 원하는 정책이라는 뜻은 아님 |
| 변경 작업 문서 | 이번 목표·범위·기준·영향·검증·현재 인계 상태 | 거대한 세션 요약을 모든 작업자에게 반복 전달하지 않음 |
| 과거 근거·원본 로그 | 이전 결정·실패·검토·원문 추적 | 현재 기준과 구분하고 새 실행의 근거로 자동 승계하지 않음 |

원하는 동작과 현재 구현이 충돌하면 차이를 문제로 기록한다. 어느 한쪽을 자동으로 덮어써서 일치한 것처럼 만들지 않는다. 예를 들어 현재 로컬 저장은 구현 사실이고, 동기화 제외는 승인된 제품 정책이 아니다.

## 변경 작업의 흐름

1. 메인이 진입점과 관련 코드·명세·이전 결정만 읽고 실제 기준 버전을 확인한다.
2. 요청을 기존 동작에 추가하는지, 바꾸는지, 데이터·다른 플랫폼까지 영향을 주는지 정리한다.
3. 핵심 정책이 불명확하면 해당 부분만 확인 대기로 둔다. 이미 답한 질문은 반복하지 않고 독립적으로 가능한 조사를 진행한다.
4. 작업 문서에 목표·변경 범위·지킬 동작·영향 계약·검증 계획을 고정한다. 작은 수정은 몇 문장으로 충분하다.
5. 메인이 직접 구현하거나, 독립 작업만 필요한 맥락과 함께 위임한다. 기준이 바뀌면 영향 작업자에게 새 버전을 전달한다.
6. 변경 영향에 맞게 검증하고 필요한 별도 리뷰를 받는다. 새 요구 누락과 구현 결함을 구분한다.
7. 기준 문서·결정·검증·사용량 연결·다음 상태를 갱신한 뒤 완료를 보고한다. 실제 표시에 사용량이 나오는지까지 확인한다.

## 작업자에게 전달할 짧은 입력 묶음

```text
작업 ID / 변경 목표 / 실제 사용자 요청·결정 근거
기준 커밋 + 현재 작업 트리 변경
관련 요구·화면·데이터/API 계약의 경로·버전
담당 파일과 변경 범위 / 다른 담당과 공유하는 자원
지켜야 할 기존 동작 / 미결정·막힌 부분
검증할 시나리오와 명령
반환할 결과: 변경·검증·위험·남은 일·근거 경로
```

전체 대화 기록은 필요한 원문 확인에만 사용한다. 새 담당자가 과거 세션을 모두 읽어야 시작할 수 있는 구조를 피한다. 인계 문서는 작업별로 유지하고 완료하면 현재 기준에 반영한다. 세션 종료 후 자동 개발·자동 재개·자동 문서 갱신이 된다고 가정하지 않는다.

## 우선 적용할 일과 평가

먼저 여백의 현재 구현·사용자 결정·미해결 동기화 요구를 분리해 진입점을 만든다. 다음 기능 수정부터 짧은 변경 문서와 필요한 경우의 리뷰를 사용한다. 기존 서버의 실제 계약을 확인하기 전에는 계정·충돌·마이그레이션 정책을 임의 확정하지 않는다.

대표 변경 몇 건에서 전체 완료 시간, 모델 사용량, 인계·대기, 재작업, 사용자 누락 지적을 비교한다. 측정 없이 새 방식이 더 빠르거나 정확하다고 확정하지 않는다. 별도 기억 서버나 검색 시스템은 문서량과 검색 실패가 실제로 문제가 될 때 검토한다.

현재 운영 지침의 선택 커밋 설치·검증 상태와 재시작 필요 여부는 [프로젝트 에이전트 운영](agent-workflow.md)의 적용 상태를 따른다. 이 제안 문서는 설치·실행 상태의 근거가 아니다.
