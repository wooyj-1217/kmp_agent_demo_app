# 프로젝트 커밋 규칙

커밋은 변경 전후를 찾는 기준이고, 메시지는 diff만으로 알기 어려운 이유와 판단을 남기는 기록이다. 현재 명세는 현재 기준으로 갱신하고 과거 변경은 Git과 관련 작업 기록으로 추적한다. 이 규칙은 프로젝트의 새 커밋에 적용한다.

## 커밋 단위

- 하나의 목적을 설명하고 검토·되돌리기 가능한 단위로 묶는다. 서로 무관한 기능·정리·환경 변경은 분리한다.
- 동작 변경에 필요한 코드·테스트·현재 명세·맥락 갱신은 함께 반영한다. 단계별로 나누면 관련 작업 기록으로 연결하고 미완료 범위를 명시한다.
- 기존 사용자 변경을 임의로 포함하지 않는다. 커밋 전 staged diff와 포함 파일을 확인한다.
- 원본 검증 로그·캡처·검증 JSON·증거 묶음은 로컬에서만 보존하며 커밋·PR 첨부·원격에 올리지 않는다. PR에는 수정 코드·문서와 검증 명령·결과 요약만 포함한다. 필요한 로컬 근거 경로와 대상 버전은 작업 기록에 연결하고, 원본 증거를 삭제·이동하지 않는다. 비밀정보는 포함하지 않는다.

## 메시지

제목은 `<type>(<scope>): <변경 요약>` 형식으로 작성한다. scope는 필요할 때만 쓰고, 설명은 한국어로 작성한다. 코드 식별자는 원문을 유지한다. 제목은 가능하면 50자 이내, 최대 72자로 구체적인 변경 동작을 표현한다.

주요 type: 기능 추가 `feat`, 결함 수정 `fix`, 동작을 유지하는 구조 변경 `refactor`, 성능 `perf`, 문서 `docs`, 테스트 `test`, 빌드 `build`, CI `ci`, 포맷 `style`, 기타 관리 `chore`, 되돌리기 `revert`. 호환성이 깨지면 `!`와 `BREAKING CHANGE:` 본문을 사용한다. 제목 끝에는 마침표를 쓰지 않고 본문 앞에는 빈 줄을 둔다.

기능·정책·데이터/API 계약·아키텍처 변경, 보안 수정, 데이터 이전, 되돌리기는 본문을 필수로 작성한다. 단순 오타·기계적 수정은 제목으로 충분하면 생략할 수 있다.

본문을 작성할 때 아래 네 필드를 각각 한 줄 이상 작성한다. 해당 사항이 없거나 미실행이면 그 사실과 이유를 적는다. `feat`·`fix`·`refactor`·`perf`·`revert` 및 `!` 제목은 훅이 본문을 필수로 검사한다. 다른 type의 의미 있는 정책 변경도 본문이 필요하며 그 판단은 사람이 확인한다.

- `이유:` 어떤 문제·요구 때문에 바꿨는지와 중요한 선택의 근거
- `영향:` 바뀐 동작, 호환성·데이터 이전, 남은 제한
- `검증:` 실제 수행한 검사와 결과, 중요한 미실행 범위
- `기록:` 추적할 실제 작업 ID·이슈·결정 기록·검증 근거 경로

없는 작업 ID나 사용자 승인·검증 결과를 만들지 않는다. 커밋 전 검증은 당시 작업 트리 검사로 표현하고, 생성될 커밋 SHA에서 검증했다고 미리 주장하지 않는다. 상세 명령·필요한 환경 설명과 로컬 로그 경로는 연결한 작업 기록에 둔다. 로그 원본은 문서에 복사하거나 커밋·PR에 첨부하지 않는다.

```text
fix(storage): 저장 실패 시 편집 내용 보존

이유: 쓰기 실패 뒤 화면이 닫혀 재입력이 필요했다.
영향: 저장 성공 후에만 닫고 실패 시 초안과 재시도를 유지한다.
검증: 작업 트리에서 저장 실패 시나리오 통과
기록: <실제 작업 기록 경로>
```

위 예시는 형식 설명이며 실제 구현·검증 근거가 아니다. 사용할 때 실제 내용으로 바꾼다.

## 과거 결정과 연결

- 이전 정책을 바꾸면 이유와 대체하는 결정 기록 또는 관련 커밋을 연결한다. 되돌리기는 대상 커밋과 되돌리는 이유를 남긴다.
- 긴 논의·로그·현재 명세를 메시지에 복사하지 않는다. 작업 기록에는 이유와 근거를, Git에는 실제 변경을 보관한다. 별도의 커밋 요약 문서를 반복 생성하지 않는다.
- 작업 기록은 관련 기능·실제 작업 ID로 찾을 수 있게 하고, 현재 맥락에는 유효한 결정과 필요한 링크만 유지한다. 과거 검증을 새 변경의 PASS로 승계하지 않는다.
- 메시지 형식을 맞추기 위해 기존 공유 이력을 재작성하지 않는다. squash할 때는 최종 diff 기준으로 메시지를 다시 작성하고 중요한 이유·결정·근거 링크를 보존한다.

## 적용 범위

추적과 문서 갱신에는 [산출물 관리 규칙](artifact-policy.md)을 함께 적용한다.

### 자동 검사 훅

Python 3와 Git이 필요하다. 새 clone에서는 저장소 루트에서 설치한다. 설치기는 기존 다른 `core.hooksPath`나 기본 위치의 활성 훅이 있으면 교체하지 않고 중단한다.

```sh
python3 tools/install_git_hooks.py
git config --get core.hooksPath
```

설정값은 `.githooks`이며 저장소 로컬 설정에만 적용한다. `.githooks/commit-msg`가 `tools/check_commit_message.py`를 호출하며 메시지를 수정하지 않고 오류 시 커밋을 중단한다. 설치를 반복할 수 있다. 설치 전 hooksPath가 없었던 경우 해제는 `git config --local --unset core.hooksPath`다. 기존 설정이 있었다면 그 값을 복원한다.

검사 범위는 제목 형식·한국어 포함·72자 제한, 본문 필드의 존재, `!`의 호환성 설명, `revert`의 대상 SHA 형식이다. 이유의 정확성·검증의 진실성·기록 경로 존재·산출물 갱신 여부는 메인이 검토한다. 일반 merge·revert 자동 메시지도 규칙에 맞춰 편집하며 fixup/squash 임시 커밋용 우회는 추가하지 않는다.

```sh
python3 tools/check_commit_message.py <메시지 파일>
python3 -B -m unittest discover -s tools -p test_commit_hooks.py -v
```

로컬 훅은 `--no-verify` 등으로 우회할 수 있으며 clone에 설정이 자동 전파되지 않는다. CI·서버 강제 검사는 이번 범위에 포함하지 않는다. 커밋·push 권한이나 공통 하네스 원본·설치된 release는 변경하지 않는다.
